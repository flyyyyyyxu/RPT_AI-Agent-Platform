> 配套文档：《Agent基建平台-笔试作答.md》《Agent开发平台-行业与产品调研.md》《竞品调研-低代码Agent平台.md》。
> 本文件说明原型怎么搭、按什么顺序、每一步用什么提示词。

> **范围：只做前端原型。** 所有数据和操作结果都是 mock，不接后端、不调用真实模型、不做真实的系统对接。详细约束见上下文文件的「技术约束」。

## 一、三个关键判断

### 1. 风格：规范前置，打磨后置

**风格规范在一开始就定下来，细节打磨放到最后。**

- **开始时定下的是「规范层」**：色板、字体和字号层级、间距、圆角、阴影、组件样式（按钮、表格、标签、卡片）。这些要做成 design tokens（设计变量），所有页面只能引用变量，不能写死数值。具体规范见 Step 0 上下文文件里的「风格规范」：A 是你的设计规范原文，B 是针对本产品补充的具体数值和规则。
- **最后统一做的是「打磨层」**：文案统一、空状态、加载态、交互细节、各页面之间的一致性。

原因：AI 生成页面时，每一轮都会有点「漂移」，这一页的按钮圆角是 8，下一页可能变成 6。如果等最后再统一风格，就要把十几个页面逐个返工，而且很难改干净。规范一开始就定成变量，后面要调整时改一处，全局生效。

### 2. 从基础框架开始，但按「一条完整链路」推进，不按「一个个模块」推进

**是的，从 Agent 开发平台的基础功能和框架开始。** 但要注意推进方式：

- ❌ 不要先把构建页做到完美，再做评测页，再做发布页。这样做到一半时间用完了，原型只有前半截，看不出闭环。
- ✅ 先搭全局框架，再用一个通用示例 Agent，把「构建 → 评测 → 发布 → 监控 → 回退」**每个环节都做一个简单版本并串通**，然后再逐层加厚。

这个顺序和笔试作答里的两层结构完全对应：

| 步骤 | 做什么 | 对应笔试作答 |
|---|---|---|
| Step 1 | 全局框架 + 设计规范 + mock 数据 | — |
| Step 2 | 用通用示例 Agent 串通基础能力主路径 | 1.1 平台基础能力 |
| Step 3 | 在同一批页面上叠加生产骨架 ①–⑩ | 1.2 生产骨架 |
| Step 4 | A、B、C 三条演示剧本 | 1.2.2 个性化需求 → 通用能力 |
| Step 5 | 全局一致性打磨 | — |

### 3. 原型的重点是生产闭环，构建页做到「够用」就行

你的调研结论是「**构建已经不是瓶颈，从试点到生产才是**」。竞品在构建上都很成熟，原型如果在构建页上花大量精力，反而会显得和扣子、Dify 没有区别。所以：

- **构建页做到够用**：表单 + 自然语言生成配置 + 代码节点，**不做画布**（OpenAI 已宣布下线 Agent Builder，画布不是壁垒）。
- **时间和亮点放在生产闭环**：尤其是能力矩阵里外部产品普遍薄弱的四项（见第二节），这是原型要让阅卷人一眼看到的差异化。

另外，笔试原型的目的是让阅卷人**看到你的判断**，所以有三个设计要点：

- **加一个「能力视图」切换**：可以只看基础能力，也可以显示生产骨架。一键切换，直观展示两层关系。
- **每个功能都带标记**：一是骨架编号徽章（如 ③），二是 MVP 或二期徽章。二期功能置灰占位、不实现交互，MVP 边界一眼可见。
- **三个团队复用同一套页面**，只换配置和数据。这本身就在证明「业务差异是配置参数，不是另做一套」。

## 二、竞品借鉴（来自你的两份调研）

### 2.1 原型要突出的四个差异化

你的能力矩阵里，外部产品普遍薄弱、而 A、B、C 恰好刚需的四项，是原型的**主角**：

| 差异化能力 | 外部产品现状 | 原型里怎么体现 | 放在哪一页 |
|---|---|---|---|
| **强制上线门槛** | 低代码平台基本没有；扣子罗盘的资源库工作流评测要求先发布版本，无法做发布前强制准入 | 候选版本可以在隔离环境跑评测；门槛不通过时发布按钮禁用，并说明原因 | 评测、发布 |
| **流量灰度 + 业务指标 AB** | 低代码平台和云厂商基本没有；Langfuse 要业务方自己写分流；Agentforce 的 A/B Testing API 还在试点 | 平台负责分流、会话粘性，版本号写入埋点，AB 报告直接展示采纳、点击等业务指标 | 发布与实验 |
| **含知识的版本快照 + 分钟级回退** | Dify 回滚要把历史版本载入草稿再重新发布；LLMOps 工具多数只管 Prompt 版本 | 版本 diff 包含知识和政策版本；回退就是**把线上指向切换到旧版本**（参照 Sierra 的即时回滚、Bedrock 的「别名指向版本」），显示回退耗时 | 发布与实验 |
| **与公司内部基建打通** | 外部产品都没有 | 页面上明确标注「数据来自公司实验平台」「已接入公司内容安全」「标注任务推送至公司标注平台」 | 各页 |

### 2.2 各页面的竞品参照

| 页面 | 参照 | 借鉴什么 |
|---|---|---|
| 工作台 / Agent 目录 | 微软 Agent 365、蚂蚁 Agentar | **Agent 目录**：每个 Agent 有负责人、等级（原型 / 生产）、权限范围、成本归属 |
| 新建 Agent | 阿里百炼、Copilot Studio、Agentar 岗位模板 | 「用自然语言描述，生成初始配置」+ 场景模板 |
| 构建 | 扣子、Dify | 「配置 + 实时调试预览」同屏的思路（扣子是三栏，我们按设计规范做成双栏：左侧主操作区放配置和步骤，右侧实时调试）；表单 + 代码节点，画布放二期 |
| 评测 | 扣子罗盘（Coze Loop）、LangSmith、百度千帆 | 评测集、评估器、实验对比的数据模型；千帆的批量任务与批量评测共用一套能力 |
| 发布与实验 | Sierra、Bedrock、Langfuse、Agentforce | 快照即时回滚；别名指向版本；production / staging 标签；版本间分流、推全量 |
| Trace 与 bad case | LangSmith、Langfuse、Sierra、Dify | Trace 树（OpenTelemetry 标准）；标注队列里一键加入数据集并改写期望输出（LangSmith / Langfuse）；Dify 标注回复（命中直接返回标注答案，对应线上干预）；Sierra 的业务专家每天审样本、做标注 |
| 设置 / 护栏 | AWS AgentCore Policy | 护栏在网关统一执行，不依赖每个 Agent 自己实现 |
| 能力组件库 | Dify、腾讯 ADP、Microsoft Foundry | 知识库管理；技能按企业、团队、个人三级管理（二期）；**工具带版本** |

> 你的调研里已经标注了「未核实」和「待验证」的部分（如 HiAgent 3.0、ADP 4.0 细节、Agentforce A/B API 的试点状态），原型页面上引用竞品时避开这些即可。

## 三、信息架构与页面清单

> 2026-09-30 按「两轴信息架构」调整，以本节为准；第四节的分步提示词保留当时的搭建过程，其中的旧导航名称（能力组件库、评测中心、运维与成本、设置）已由本节替代。

**一级导航：** 工作台 / 资产中心（二级目录：知识库、数据库、工具、评测集、模型、Prompt 模板，常驻展开）/ 监控与成本 / 治理 / 模板广场（二期，置灰）

**Agent 详情页**是核心，顶部固定显示「Agent 名称 + 负责人 + 等级 + 版本选择器 + 线上指向」。下面按设计规范做成**生命周期步骤导航**：构建（发布过后叫「构建与调优」）→ 评测 → 发布与实验 → 观测（「监控」「Trace 与 bad case」两个标签页）→ ↺ 下一轮，每一步显示完成状态；观测和评测里发现的问题可以「发起优化」，带着本轮优化目标回到构建与调优；「设置」放在步骤导航末尾，不计编号。桌面端构建页是「Prompt / 能力配置 / 调试」三栏，其余页面是「主操作区 + 右侧辅助信息区」的双栏布局：

|---|---|---|---|

| 设置（Agent 内） | 基础资料 | ✓ | ⑦ 执行模式、限流、转人工 ⑨ 护栏规则 ⑩ 配额和预算 |
| 资产中心 | 知识库（页内知识库目录：团队 → 知识库 → 版本）、数据库、工具、评测集、模型、Prompt 模板；每类都有新建和详情抽屉，修改时选「发布新版本」或「修改当前版本」 | ✓ | ① 知识版本和生效时间、工具 / 模型 / 模板 / 评测集版本 |
| 监控与成本 | 跨 Agent 运行表、团队预算与配额、限流与降级一览 | ✓ | ⑦ 资源隔离 ⑩ 预算、配额 |
| 治理 | 角色与授权、护栏覆盖、审计日志 | ✓ | ⑨ 护栏覆盖 ⑩ 审计 |

## 四、搭建步骤与提示词

### 通用技巧

1. **先建一个上下文文件，每次对话都附上。** 这是防止 AI 漂移最有效的办法（模板见 Step 0）。
2. **一次只做一个步骤。** 每步完成后自己点一遍、截图检查，没问题再进入下一步。
3. **让 AI 先说计划，再写代码。** 每个提示词结尾都要求它先列出要改哪些文件、做哪些组件。
4. **反馈要具体。** 不要说「优化一下」，要说「发布页的回退按钮应该放在版本历史每一行的右侧」。

### Step 0｜准备上下文文件（PROJECT_CONTEXT.md）

这份文件已经单独保存在同一个文件夹里（`PROJECT_CONTEXT.md`），内容和下面完全一样。**每一轮对话都附上它**；以后要改规范，直接改那个文件就行。

```markdown
# 项目上下文（每次对话都附上）

## 产品
公司级 Agent 基建平台，内部平台，面向业务团队。
一句话定位：外部平台解决「怎么把 Agent 做出来」，我们解决「公司内任何团队做出来的 Agent，
怎样用同一套标准安全上线、持续变好，并把能力沉淀给下一个团队」。
纯前端原型，所有数据为 mock，每个页面右上角标注「演示数据」。

## 两层结构
- 平台基础能力（任何 Agent 都有）：构建、评测、发布、运行、观测、治理
- 生产骨架（10 项，从业务中抽象）：
  ① 变更与版本管理 ② 上线前评测验证 ③ 受控发布 ④ AB 实验与效果度量
  ⑤ 回退与下线 ⑥ bad case 归因与优化 ⑦ 运行保障 ⑧ 可观测与可追溯
  ⑨ 输出安全护栏 ⑩ 合规与成本

## 原型的四个主角（外部产品普遍薄弱的差异化能力，视觉上要突出）
1. 强制上线门槛：候选版本可以先评测，门槛不通过时发布按钮禁用
2. 流量灰度 + 业务指标 AB：平台分流、会话粘性、版本号写入埋点
3. 含知识的版本快照 + 分钟级回退：回退 = 把线上指向切换到旧版本
4. 与公司内部基建打通：实验平台、内容安全、标注平台、监控

## 核心对象
Agent 版本：不可修改的快照，包含模型、Prompt、编排、工具（带版本）、知识版本、输出格式、运行策略。
「线上指向」：生产环境当前指向哪个版本。发布和回退都是改变指向。

## 示例 Agent（mock 数据）
- 通用示例｜内部制度问答助手：在线、多轮、低风险；等级：生产；线上指向 v3
- A｜社区穿搭灵感 Agent：在线、高并发；指标：采纳率、点击率、7 日留存、P95 延迟；线上 v12，灰度 v13（10%）
- B｜生态守护 Agent：批量；指标：分类别召回率和误判率、红线样本通过率、申诉改判率；线上 v7（政策库 2026-09 版），v8 待发布
- C｜电商售后答疑 Agent：多轮会话；指标：解决率、满意度、转人工率、过期知识命中数；线上 v21（售后知识 v34）
每个 Agent 都有：负责人、所属团队、等级（原型 / 生产）、本月成本。

## 标记规则
- 生产骨架能力旁显示编号徽章，如 ③
- 每个功能显示「MVP」或「二期」徽章；二期功能置灰占位，不实现交互

## 风格规范

### A. 设计规范

为「Agent 基建平台」设计一套明亮、专业、亲和的 SaaS 工具产品界面。
目标用户是公司内各业务团队的产品、运营、算法和开发人员。
所有文案、图像和业务流程都使用本产品的实际内容。

1. 视觉基调：浅灰白页面背景、白色内容卡片、深灰正文；以珊瑚红作为唯一主要操作色。
   暖橙、靛蓝、翠绿仅用于区分功能类别、步骤或状态，避免大面积同时使用多种强调色。
2. 字体层级：中文优先 Noto Sans SC，英文和数字用 Inter。页面标题粗体、字距紧凑；
   正文清晰易读；辅助说明使用较浅的灰色。每个主要区块采用「小标签、明确标题、一句解释、具体内容」的信息层级。
3. 页面布局：内容居中并限制最大宽度，保留充足留白。
   平台首页（可选）采用左侧价值主张与行动按钮、右侧真实产品界面预览的首屏；
   后续用价值卡片、流程步骤、功能展示和底部行动区介绍产品。
   工作台页面采用清晰的步骤导航，桌面端优先使用主操作区与右侧实时预览或辅助信息区的双栏布局。
4. 组件语言：卡片使用白底、细灰边框、轻阴影和柔和圆角；输入框、选项卡和标签保持统一圆角与间距。
   主按钮使用珊瑚红实底，次按钮使用白底描边。选中状态必须同时通过边框、背景和文字体现，不能只依赖颜色。
5. 交互反馈：为加载、空状态、错误、成功及不可操作状态设计明确反馈。
   动画保持轻量，以淡入、轻微位移和悬停阴影为主，不妨碍阅读或操作。
6. 响应式：宽屏可用双栏和卡片网格；窄屏改为单列，导航折叠，按钮与表单保持易点击、易阅读。
   特别检查预览对比区（版本对比、AB 报告、diff），避免固定多列造成横向溢出。
7. 内容要求：使用本产品真实的功能名称、用户任务和示例数据；按钮文案直接说明动作
   （如「运行评测」「回退到 v12」），避免空泛的营销术语。优先展示真实界面或可信的界面示意图。

  数字使用等宽数字（tabular-nums）
- 间距：4 / 8 / 12 / 16 / 24 / 32 / 48
- 圆角：卡片 12；输入框、按钮、标签 8；徽章 6
- 阴影：卡片 0 1px 2px rgba(16,24,40,.06)；悬停 0 4px 12px rgba(16,24,40,.08)
- 布局：内容最大宽度 1440；左侧导航宽 224，可折叠到 64；右侧预览区宽 400–480
- 断点：≥1280 双栏；768–1279 右侧区收为抽屉；<768 单列、导航折叠
- 动效：150–200ms ease-out，位移不超过 4px；系统开启「减少动态效果」时关闭动画

B2 状态语义（全站统一，不能混用）
- 线上 / 通过：翠绿
- 灰度中 / 进行中：靛蓝
- 待审批 / 警告：暖橙
- 阻断 / 失败 / 错误：错误红 + 图标
- 草稿：灰色
- 二期：灰色虚线边框，整块置灰且不可点击，悬停提示「二期建设」

B3 数据类组件
- 表格：行高 48，表头浅灰底，数字右对齐，长文本截断、悬停显示全文
- 指标变化：**颜色表示好坏，不表示涨跌**。延迟上升是坏事，用错误红；采纳率上升是好事，用翠绿；
  同时显示 ↑↓ 箭头和数值
- 图表：旧版本用灰色，新版本用靛蓝，门槛线用暖橙虚线；必须有图例和数据标签
- 版本 diff：新增行翠绿浅底，删除行错误红浅底，使用等宽字体
- Trace 树：缩进表示层级，每一步带耗时条；异常步骤显示错误图标

B4 本原型专属标记
- 骨架编号徽章 ①–⑩：浅灰底、深灰字、小尺寸，不抢主操作
- 「四个主角」：卡片左侧 3px 靛蓝色条 + 「差异化」小标签（不用珊瑚红，珊瑚红只留给操作）
- MVP 徽章：描边样式；二期徽章：灰色虚线
- 「演示数据」：页面右上角浅灰小标签
- 「已接入公司 XX 平台」：辅助说明文字 + 链接图标

B5 操作层级
- 每个区域最多一个珊瑚红主按钮
- 回退、下线、暂停这类影响线上的操作：次按钮样式 + 页面内二次确认（说明影响范围），
  不用浏览器弹窗，也不用红色实底
- 不可点击的按钮必须说明原因，比如「评测门槛未通过」

B6 图标与文案
- 图标统一使用 Lucide，线宽 1.5，尺寸 16 / 20
- 界面语言为中文；Agent、Prompt、Trace、bad case、AB 等术语保留英文
- 时间格式 2026-09-28 16:13；百分比保留一位小数；版本号写作 v12
- 只做浅色模式

## 技术约束（只做前端）
- 纯静态前端：Vite + React + Tailwind（或单文件 HTML）。
  不使用 Next.js 的 API 路由、Server Actions 等服务端功能；不写任何后端代码；不使用数据库
- 不调用任何真实的模型 API 或外部接口。调试台输出、自然语言生成配置、运行评测、批量任务的结果，
  都从 mock 数据里读取预设结果，并配 0.5–1.5 秒的模拟加载
- 「发布」「回退」「放量」「审批」等操作只改变前端状态，页面上显示相应的变化
- 「已接入公司 XX 平台」「版本号已写入埋点」只是界面上的说明文字，不做真实对接
- 上传文件：只在前端读取文件名和行数，然后展示预设结果；下载：导出预设的 CSV
- 状态保存在前端内存里；可以用 localStorage 保留演示进度（读写失败时不影响使用）；
  全局提供「重置演示」按钮，一键恢复初始数据
- 所有颜色、字号、间距只能引用 B1 的设计变量，不许写死数值
- 字体通过 Google Fonts 引入；图标使用 Lucide
- mock 数据放在 `src/data`：`base/` 按功能拆分，`scenarios/` 按演示剧本拆分，统一从 `src/data/index.ts` 导出；页面、组件和逻辑层只从这个入口引用
- 构建产物是静态文件，可以直接部署到静态托管打开，不需要启动服务端

## 部署约束（保证随时能打包成单个 HTML）
- 使用 vite-plugin-singlefile，`npm run build` 输出一个自包含的 dist/index.html（JS、CSS 全部内联）
- Vite 配置 base: './'，所有资源用相对路径
- 路由用 HashRouter（网址形如 #/agents/a），或者直接用页面状态切换；不用 BrowserRouter
- 不用动态 import 和代码拆分；所有依赖打包进来，运行时不从外部 CDN 加载脚本
- 图片优先用内联 SVG 或小图，避免单文件体积过大
- 字体：Google Fonts 加载失败时回退到系统字体（PingFang SC、Microsoft YaHei、sans-serif）
- 本地存储：所有读写都包在 try/catch 里，不可用时页面照常工作

## 代码组织
- 按功能分文件夹：`src/features/<功能>/` 放该功能的页面、专用组件和专用样式
- 跨页面复用的组件和样式放 `src/shared/`：设计变量、基础样式、按钮、徽章、能力卡片等
- 与界面无关的状态、规则和取数放 `src/core/`：`store/` 演示状态与操作，`rules/` 版本、门槛、生命周期、演示时钟，`data-access/` 统一取数（演示剧本在这里替换数据）
- mock 数据放 `src/data/`（见技术约束）
- 依赖方向：features → shared → core → data → types，只允许从左往右引用；功能之间尽量不互相引用，例外是公共外壳 `features/shell` 和剧本锁定 `features/playbook/playbooks`
- 改完运行 `npm run smoke`（三条剧本 + 回归检查）；涉及样式时运行 `npm run snapshot:compare`，与改动前的基准截图比对
```

## 五、时间分配建议

| 步骤 | 占比 | 说明 |
|---|---|---|
| Step 0–1 框架与规范 | 15% | 规范定得越早，后面返工越少；组件样板页检查通过再往下走 |
| Step 2 基础能力主路径 | 20% | 先保证闭环能走通，构建页做到够用即可 |
| Step 3 生产骨架 | 30% | 原型的核心，四个主角都在这一步 |
| Step 4 三条剧本 | 20% | 讲解时最有说服力 |
| Step 4+ 平台首页（可选） | 5% | 阅卷人的第一屏 |
| Step 5 打磨 | 10% | 最后统一收尾 |

> 如果时间紧张，先砍平台首页，再砍 Step 4 里的剧本数量（保留一条最完整的，比如 B，它同时覆盖主角 1、2、3）。不要砍 Step 3 的四个主角、「能力视图」切换和 MVP/二期标记。
